## 現況落差

現行 `SupervisionReport` 的設計是「一個 `summary` 大欄位裝所有內容」：

```prisma
model SupervisionReport {
  reportDate DateTime
  weather    String?   // 單一字串
  summary    String?   // 按圖施工概況（實際上什麼都塞這裡）
  manpower   String?
  equipment  String?
  keyNotes   String?   // 重要事項
  filedBy    String?
  status     ReportStatus
}
```

而法定日報是**五個固定章節 + 一張數量表 + 三態勾選 + 上下午天氣 + 當日進度 + 表報編號 + 簽章**。逐項對照：

| 範例中的內容 | 現況 | 落差 |
| --- | --- | --- |
| 表報編號 001 | 無 | 缺流水號 |
| 今日天氣（上午／下午） | `weather` 單一字串 | 無法判定半天雨 |
| 預定進度／實際進度 | 無 | 缺當日進度 |
| 一、工程進行情況＋**數量表** | 塞 `summary` | **最大缺口**，數量完全非結構化 |
| 二、監督依照圖說施工 | 塞 `summary` | 章節未分離 |
| 三、查核材料規格及品質 | 塞 `summary` | 章節未分離 |
| 四、職安衛（三態勾選） | 塞 `summary` | 無法統計 |
| 五、其他約定監造事項 | `keyNotes` | 語意接近但非同一件事 |
| 免計工期宣告 | 塞 `summary` | 有法律效果卻無法統計 |
| 監造單位簽章 | 無 | 缺簽章 |
| 施工照片 | `MediaAsset` 僅掛 Project | 無法歸屬某日日報或某一施工項目（見 E8） |

## 擴充項目（依價值排序）

### E1. 數量表 — 最高價值

> 【定案 A】日報加總為月報累計/逐工項完成的**權威來源**；月報原訂 `WorkItemPeriodSnapshot` 快照取消，`WorkItem.completedQty` 降為推導/唯讀。此為第 1 階與月報的合流點。

範例的核心。新增子表逐日記錄各工程分項的「本日完成數量」：

```prisma
model SupervisionReportItem {
  id         String   @id @default(cuid())
  reportId   String
  workItemId String?  // 對應工程分項；允許 null 以容納契約外臨時項目
  /// 施工項目名稱快照（workItem 更名或刪除後仍可還原當時報表）
  itemName   String
  unit       String?
  /// 本日完成數量（累計由系統加總，不另存以免對不起來）
  dailyQty   Decimal
  note       String?
  sortOrder  Int      @default(0)

  report   SupervisionReport @relation(fields: [reportId], references: [id], onDelete: Cascade)
  workItem WorkItem?         @relation(fields: [workItemId], references: [id], onDelete: SetNull)

  @@index([reportId])
  @@index([workItemId])
}
```

設計要點：

- **只存「本日完成」，不存累計**。累計 = 期初 + Σ 本日；存兩份必然對不起來。範例中的「契約數量」「累計完成數量」都由系統推導：契約數量取 `WorkItem.contractQty`，累計取「該工項至當日的 `dailyQty` 總和」。
- **`itemName` / `unit` 為快照**。工程分項日後更名或刪除，歷史日報仍須還原當時內容（法定文件不可回溯改寫）。
- **`workItemId` 可為 null**，容納契約外的臨時項目（範例的「化冀池打除」「連接管埋設」未必都在台帳上）。

**這一項同時補上月報的缺口。** 先前月報「逐工項本期完成百分比／金額」因無期末快照而顯示 `—`；有了逐日數量後，**本期完成量 = 期間內該工項 `dailyQty` 之和**，不需另建 `WorkItemPeriodSnapshot`。日報本身就是天然的流水帳。

### E2. 五個法定章節拆開

```prisma
  /// 一、工程進行情況（數量表以外的文字敘述）
  workProgress   String?
  /// 二、監督依照設計圖說及核定施工圖說施工
  designCompliance String?
  /// 三、查核材料規格及品質
  materialQuality  String?
  /// 五、其他約定監造事項
  otherMatters     String?
```

（第四章為職安衛，見 E3。）現行 `summary` 保留作為第一章的敘述欄位（`workProgress`）或於遷移時搬移；`keyNotes` 對應第五章。

好處：各章可獨立留白（範例二、三章即為空白）、可獨立稽核、月報彙整時可按章分類。

### E3. 職安衛三態勾選

範例：`✅已完成 □未完成 □無施工`——三態列舉，非自由文字。

```prisma
enum SafetyCheckStatus { COMPLETED NOT_COMPLETED NO_WORK }

  /// 四（一）施工廠商施工前檢查事項辦理情形
  safetyPreCheck SafetyCheckStatus?
  /// 四（二）其他工地安全衛生督導事項
  safetyNotes    String?
```

價值：可統計「本月施工前檢查完成率」，是實用的稽核指標；且 `NO_WORK` 正好對應停工日，可與 E5 交叉驗證。

### E4. 天氣拆上午／下午（選配）

> 【定案 D】天氣僅供紀錄、**不作停工判定**（判定看 `summary` 與 E3/E5 旗標）。原「半天雨→展延」的理由不再成立，本項降為選配的紀錄強化，非必要。

```prisma
  weatherAm String?
  weatherPm String?
```

實際意義是**半天雨的判定**——直接關係工期展延爭議。現行 `classifyWorkDay()` 只看單一字串，拆開後可判定「上午雨停工、下午復工」這類情形。

> 遷移策略：保留 `weather` 一段時間，新欄位為主、舊欄位僅供既有資料讀取，避免破壞歷史紀錄。

### E5. 當日預定／實際進度與免計工期

> 【定案 C，2026-08-07 修正】`plannedProgress`（當日預定）**改為系統自動帶入**，使用者每日只填實際。
> 來源為**既有**的工程分項基準（工項 `plannedStart`／`plannedEnd` 線性展開，見 `scurve.ts` 的 `plannedFrac`），
> **不需要新增 schema 或設定介面** —— 先前「需新增專案預定進度設定」的判斷已修正。
> 實作方式為抽出 `plannedProgressAt(items, date)` 純函式。詳見 `日報月報計劃整合檢視.md`〈決策 C 的修正〉。
> 【定案 D】`excludedFromDuration` 是停工/免計工期的**權威旗標**，統計以它為準（非解析 `summary` 文字），故表單須確保此旗標「一鍵好勾」。

實際落地的 schema **只有免計工期兩欄**：

```prisma
  /// 是否免計工期（有法律效果，須可統計）
  excludedFromDuration Boolean @default(false)
  /// 免計工期之契約依據，如「工程契約書第 7 條」
  exclusionBasis String?
```

> **`plannedProgress` 與 `actualProgress` 最終未新增欄位**（2026-08-07）。
> 原計劃把兩者設計為儲存欄位，實作時確認它們是「方便目視進度與繪圖」的判讀輔助，
> 並非日報上具法律效力的載明值 —— 存下來就變成儲存推導值，
> 與決策 F「不存推導值」相衝突，且會與數量修正後的推導結果不一致。
>
> 兩者改為即時推導（`supervisionReport.service` 的 `getDailyProgress`）：
> 預定用 `plannedProgressAt`（工程分項基準，與月報同基準），
> 實際用「期初 + Σ **截至該日**的日報數量」。取「截至該日」而非「截至今日」，
> 否則補填舊日報時整份歷史會顯示同一個今日數字。
>
> 若需保存核定當下的數字，正解是**月報定稿時凍結整份報表**（決策 J-a 已實作），
> 而非在日報上零散存欄位。

`excludedFromDuration` 是重點：範例二寫「依據工程契約書第 7 條本日不予施工及其相關規定免計工期」，這是**法律效果的宣告**，不只是描述。做成布林才能算出「本期免計工期共 N 天」——該數字在結算時有金額意義。

逐日 S-Curve 仍然可行且不需新欄位：`plannedProgressAt` 可取任意日期的預定值，
實際值則由「截至該日的日報數量」推導，兩者皆為即時計算。
比現行月度分桶精細得多，屬後續的呈現層工作。

### E6. 表報編號與簽章

> 【定案 E】表報編號確認**由系統自動產生流水號**（依 `reportDate` 決定論排序），無人工編號。此項不依賴簽核流程，可獨立先行。

```prisma
  /// 表報編號（專案內流水號，決定論產生）
  serialNo Int?
  /// 簽章：關聯既有簽核流程
  approvalDocumentId String?
```

編號依專案內 `reportDate` 排序決定論產生（避免人工編號衝突）；簽章建議接既有 `ApprovalDocument`，不另造機制。

### E7. AI 判讀協助填報（新增，2026-08-05）

> 起因：確認現行日報**沒有** AI 文字／欄位判讀。`report-dialog-fields.tsx`／`report-file-form.tsx`／`report-edit-form.tsx` 的「帶入當日查驗/缺失」是 `suggestReportAction` → `reportService.suggestReport()`，屬**資料庫查詢**，不讀文件或圖片、無模型參與；`report-generator.tsx:10` 亦註明「日報改由人工填報，AI 僅彙整週/月/季/年報」。
>
> 但系統已有兩套現成的判讀機制，日報只是沒接上。E7 即為接線工作，**非從零開發**。

本項直接支撐〈表單改造原則〉的「欄位膨脹的代價極高」問題：E1 數量表加上五章後，若只靠逐格人工輸入，實務上會導致「隨便填」或「不填」。若監造手上已有紙本日報、包商施工日誌或現場照片，判讀後預填會比逐格鍵入快得多。

分兩層，成本與價值差異明顯：

#### E7-a 單筆欄位判讀（低成本，建議優先）

沿用既有**表單助手**（`form-assist`），只需新增一份規格：

- `src/constant/form-assist.ts` 的 `SPECS` 陣列增加 `id: "supervision-report"` 一筆，欄位含 `reportDate`／`weather`／五章文字（E2）／`plannedProgress`・`actualProgress`（E5）／`safetyPreCheck`（E3，`kind: "select"` 三態）。
- `FormAssistId` 型別加上 `"supervision-report"`（寫錯 id 編譯期即報錯）。
- 日報表單掛 `useFormAssist({ assistId: "supervision-report", ... })`，比照 `create-record-dialog.tsx`／`obligation-detail.tsx`。

無須新增 API 或 service：`/api/forms/assist` 為通用路由，已處理歸檔、Office 轉文字、PDF／影像原生 inlineData、`sanitizePatch` 欄位驗證。

既有機制自帶的護欄（**不需重造**）：

| 護欄 | 既有行為 |
| --- | --- |
| schema 不可由前端自訂 | 前端只送 `specId`，規格伺服器端查表 |
| 型別／選項／日期驗證 | `sanitizePatch` 不合法者丟棄並列入 `rejected`，不硬塞 |
| 不覆蓋人工輸入 | `planFill` 已填欄位一律不覆蓋 |
| 附件留存 | `archiveAttachment` 即使判讀失敗仍歸檔為專案文件 |
| 稽核 | `withLogContext` 記錄 route／user／conversation |

**排除欄位**（比照既有規格慣例）：`projectId`（表單自帶）、`workItemId` 等指向其他紀錄的 id（執行期 DB id，模型無從判讀，硬填只會產生錯誤關聯）。`serialNo` 亦排除——依決策 E 由系統產生。

#### E7-b 數量表多列判讀（較高成本，價值最大）

**E1 數量表是多列的，表單助手是「單筆欄位」機制，不適用。** 多列判讀的前例是**建置精靈**（`wizardExtract.service.ts`）：從單一文件判讀出多筆 `scopeItems`／`obligations`／`workItems`，以 async generator 分段產出、單段失敗不影響其他段（`faith.extractScopeItems`／`extractWorkItems` 等）。

日報數量表比照此模式，但有一個**日報特有的難點**：判讀出的品項須**對應到既有 `WorkItem`**才有意義（否則 `workItemId` 全為 null，無法加總、月報 3.3 也接不上）。因此需要一道**比對步驟**：

1. 判讀文件 → 得到「品項名稱 + 數量 + 單位」的候選列。
2. 以名稱對既有 `WorkItem` 清單做比對（可參考 `domain-match.ts` 既有做法），產生「建議對應的工項」。
3. **對應結果須人工確認**——比對不確定者標記待確認，不自動寫入 `workItemId`。契約外臨時項目則維持 `workItemId: null`（E1 已允許）。
4. `unit` 一律取自 `WorkItem.unit`（不採信文件上的單位），與 E1〈風險〉的單位一致性要求一致。

> 決策 A 使日報加總成為月報累計的**權威來源**，判讀錯誤會直接污染月報金額與進度。故 E7-b 必須維持「**判讀只做預填、人工確認後才入帳**」，不可自動送出。

#### 階段定位

E7-a 可在 E2／E3／E5 欄位落地後隨即接上（成本低）。E7-b 建議待 E1 數量表與月報串接穩定後再做，避免判讀錯誤與資料架構變動同時進行、難以歸因。

### E8. 施工照片存儲（新增，2026-08-05）

> 決策：照片**可綁定到數量表的個別工項**（非僅整份日報），使查核時能逐項舉證。

#### 現況：已有照片模型，但掛錯層級

`MediaAsset` 已存在且具照片語意，然而**只關聯 Project，無法歸屬某一份日報**：

```prisma
model MediaAsset {
  projectId  String
  title      String
  type       MediaType @default(PHOTO)   // 已預設為照片
  category   String?
  fileUrl    String?                     // 存 storedName
  fileSizeKb Int?
  capturedAt DateTime?                   // 拍攝時間（對監造照片有舉證意義）
  // 無 reportId、無 reportItemId、無 deletedAt
}
```

#### 需先定案：以哪個檔案系統為底

專案內有兩套檔案模型，**`documents.service.ts:97` 已將 MediaAsset 標註為「舊版數位檔案上傳／管理／閱覽」**：

| | `MediaAsset`（舊版） | `ProjectFile`（現行） |
| --- | --- | --- |
| 照片語意 | ✅ `type PHOTO`／`category`／`capturedAt` | ❌ 僅 `createdAt`（上傳時間，非拍攝時間） |
| 資料夾樹 | ❌ | ✅ `FileFolder` |
| 軟刪除 | ❌ `remove()` 為 `prisma.mediaAsset.delete`（**實刪**） | ✅ `deletedAt` |
| 儲存欄位 | 較粗（`fileUrl`＋`fileSizeKb`） | 對齊 `SavedFile`（`fileName`／`storedName`／`mimeType`／`size`） |
| 儀表板統計 | ✅ `dashboard.service` 已計數 | — |

**建議以 `ProjectFile` 為底、補 `capturedAt`**，理由有二：

1. **法定文件不可回溯改寫**（本文 E1 已據此要求 `itemName` 快照）。日報照片是舉證資料，`MediaAsset` 的**實刪**與此原則相衝突；`ProjectFile` 已有 `deletedAt`。
2. MediaAsset 既標為舊版，在其上新建具法律意義的功能會累積遷移債。

> 但這是架構決策，若團隊實際打算保留 MediaAsset 作為影像專用模型，則改為「擴充 MediaAsset：補 `reportId`／`reportItemId`／`deletedAt`」亦可行。**請先定案再施作。**

#### 綁定設計（兩層，`reportItemId` 選填）

```prisma
  /// 所屬日報（照片歸屬某日）
  reportId     String?
  /// 所屬數量表列（選填；指定後即為該施工項目的舉證照片）
  reportItemId String?

  report     SupervisionReport?     @relation(fields: [reportId], references: [id], onDelete: SetNull)
  reportItem SupervisionReportItem? @relation(fields: [reportItemId], references: [id], onDelete: SetNull)

  @@index([reportId])
  @@index([reportItemId])
```

要點：

- **`onDelete: SetNull` 而非 Cascade**：日報若被刪除，照片本身仍是專案資產，不應連帶消失（與 E1 的 `SupervisionReportItem` 用 Cascade 不同——那是報表的組成部分，照片不是）。
- **`reportItemId` 須與 `reportId` 一致**：指定 `reportItemId` 時，其所屬 report 必須等於 `reportId`。此為應用層檢核（DB 無法直接約束），否則會出現「A 日報的照片掛到 B 日報的工項」。
- **`capturedAt` 與 `reportDate` 不一致時提示**：拍攝日與報表日不同是常見的補登情形，不應阻擋，但**應提示**——照片的拍攝時間在工期爭議中有舉證意義，靜默接受會讓錯誤無從察覺。

#### ⚠️ 阻礙：HEIC 完全不支援

**這會直接妨礙「工地用手機拍照上傳」的核心使用情境。** 現況：

- `storage.service.ts` 的 `ALLOWED_EXT` 僅 `application/pdf`／`image/png`／`image/jpeg`；`ALLOWED_ACCEPT = ".pdf,.png,.jpg,.jpeg"`。
- 較寬的 `upload-policy.ts` 的 `EXT_BY_MIME` 也只到 `png`／`jpeg`／`webp`／`gif`。
- **`heic` 在整個 codebase（含 prisma schema）查無任何字樣。**

而 **iPhone 相機預設輸出即為 HEIC**。監造在工地以手機拍照後直接上傳會被拒收，且錯誤訊息（「不支援的檔案格式」）不會告訴他該怎麼辦。

三種處理方式，須擇一定案：

| 方案 | 說明 | 代價 |
| --- | --- | --- |
| **伺服器端轉檔** | 上傳後轉為 jpeg 存檔（保留 EXIF 的 `capturedAt`） | 需引入 HEIC 解碼相依（如 `heic-convert`／`sharp` 含 libheif），體積與部署成本 |
| **前端轉檔** | 瀏覽器端轉 jpeg 再上傳 | 相依較輕，但行動裝置效能與相容性風險 |
| **僅放行白名單並明確提示** | 加入 `image/heic`／`image/heif` 至白名單原樣存檔，並在 UI 指引使用者改設定 | 最省事，但 HEIC 無法在多數瀏覽器內嵌預覽，等於存了看不到 |

> 建議**伺服器端轉檔**：唯一能同時滿足「使用者不必改手機設定」與「照片可在系統內預覽」的做法。另可順道自 EXIF 讀出拍攝時間自動帶入 `capturedAt`，省去人工填寫。

#### 其他待確認

- **`category` 分類語彙**：施工照片慣例會分「施工前／施工中／完工」（三階段對照是監造照片的標準做法）。若採用，應為列舉而非自由文字，否則無法統計與比對。
- **檔案大小與張數上限**：日報照片量大（一日數十張），須訂上限並考慮縮圖，否則儲存區與頁面載入都會失控。
- **儲存區容量**：`storage.service` 目前寫入本機 `storage/uploads`。照片量級與文件不同，S3 遷移的時程宜及早評估（`storage.service` 的註解已預留「Swap the implementation (e.g. S3) without changing callers」）。

## 表單改造原則

**日報是每天都要填的，欄位膨脹的代價極高。** 加入五章＋數量表後，若全靠人工輸入會變成填空地獄，實務上會導致「隨便填」或「不填」——那比欄位不足更糟。

因此表單改造與 schema 擴充**必須同時進行**：

- **數量表預帶清單**：開啟表單即列出該專案所有工程分項（含單位、契約數量、目前累計），監造只需在「本日完成」填數字，未施工者留空。

### 數量錄入的填寫設計（E1 的表單面，2026-08-05 補強）

> 「錄入工程項目」即 E1 數量表的**填寫本日完成數量**，非新增資料模型。以下為避免「填空地獄」的具體要求。
>
> **實作狀態（2026-08-08 核對）**：上方進度表把 E1 標為完成，指的是
> schema、推導層、台帳與月報接線、以及可用的填報介面。
> 本節列出的表單體驗要求**尚有三項未做**，逐項標示於下 ——
> 不標示的話，E1 的 ✅ 會讓人以為表單面已經收尾。

| 要求 | 狀態 |
| --- | --- |
| 只顯示會用到的列 | ✅ `showAll` 切換，預設只展開已填（含已填備註）的列 |
| 單位唯讀、就地顯示 | ✅ 且伺服器端強制以 `WorkItem.unit` 覆寫，不採信前端 |
| 當場顯示「累計 = 期初 + Σ 本日」 | ✅ 「填報後累計」欄 |
| 當場顯示**佔契約數量的百分比** | ⬜ **未做**：目前只有絕對數字 |
| 超出契約數量提示而非阻擋 | ✅ |
| 契約外臨時項目、不進台帳 | ✅ |
| 備註可讀可寫 | ✅（2026-08-08 補；先前表單讀不到 `note`，整張表送出會把它寫成 null） |
| **沿用前一日（只帶項目、不帶數字）** | ⬜ **未做** |
| **停工日一鍵歸零／一鍵套用** | ⬜ **未做**（`stopReason` 欄位已就位，缺的是連動動作） |
| 章節可折疊 | ⬜ 相依 E2，尚未拆章 |

各項要求的理由：

- **只顯示會用到的列**：專案工程分項可能數十列，全部展開會讓每日填報變成長表捲動。預設**只展開本日有施工的列**，其餘收合於「其他工項」之下可展開；或提供搜尋／篩選。
- **單位唯讀、就地顯示**：`unit` 由 `WorkItem.unit` 帶出且**不可編輯**（見〈風險〉的單位一致性要求），與數量欄並列顯示，避免填錯量級（如把 m 當成 m²）。
- **當場顯示推導結果**：填入本日完成後，即時顯示「累計 = 期初 + Σ 本日」與佔契約數量的百分比。監造當下就能看出數字是否合理，而非等月報彙整才發現異常。
- **超出契約數量須提示而非阻擋**：累計超過 `WorkItem.contractQty` 常見於契約變更或數量增減，**不應阻擋**（會逼使用者亂填），但應明顯提示以促成確認。
- **契約外臨時項目**：E1 已允許 `workItemId` 為 null。表單須提供「新增契約外項目」列，填 `itemName`／`unit`／數量。**此列不進入台帳**，僅存在該日報中——若要成為正式工項，仍須經台帳（`ledger-view`）建立，避免日報成為工項的旁路建立途徑而繞過契約管控。
- **備註**：備註常是免計工期或數量異常的唯一書面理由。表單若讀不到它，整張表送出時會把它寫成 null —— 使用者只是開啟日報存個檔，就刪掉了一句自己從沒看過的話。
- **沿用前一日數量**：連續同類工作可「複製前一日」帶出相同工項清單（**只帶項目、不帶數字**）。帶數字會讓錯誤沉默地累積成累計值，而累計值依決策 A 是月報金額的權威來源。
- **停工日一鍵套用**：勾選停工原因後，自動將數量表全部歸零、並帶出免計工期欄位。`stopReason`（決策 H）與 `excludedFromDuration`（E5）欄位都已就位，缺的只是表單上的連動。
- **沿用並強化既有自動帶入**：目前已有「帶入當日查驗」「帶入當日缺失」兩個按鈕（`report-dialog-fields.tsx`），方向正確；擴充後應延伸到第二、三章（查驗紀錄 → 監督施工；試驗報告 → 材料品質）。此為**資料庫帶入**，與 E7 的**文件判讀**互補而非重複：前者用系統既有紀錄、後者用外部文件。
- **章節可折疊**：空白章節預設收合，避免視覺壓迫（相依 E2）。

## 風險與待確認

- **既有資料搬移**：`summary` 目前混裝多章內容，自動拆分不可靠。建議 E2 採「新欄位為主、`summary` 保留為 legacy 顯示」，不做自動拆解；或提供人工複核介面。
- ~~**數量表與台帳的一致性**~~ → **已定案並實作（決策 A）**：日報加總為權威。
  `WorkItem.completedQty` 語意收斂為**期初累計基準**，台帳上可編輯的是期初、
  當前有效累計為推導值且任何路徑都不回寫。
  期初仍須可編輯（導入日報前已完成的量只能由此登錄），
  但已有日報計入時修改期初會改寫歷史月報所依據的數字，故 UI 明確確認。
- ~~**`unit` 一致性**~~ → **已實作（決策 L）**：數量表的單位一律由伺服器端取自
  `WorkItem.unit`，不採信前端；且工項一旦被日報引用即禁止修改 `unit`
  （守門置於 `updateLedgerQty`，不分報表狀態一律計入）。
- **免計工期認定**：`excludedFromDuration` 具法律效果，其判定與契約依據宜由監造確認，不應由系統推測。
- ~~**職安衛三態與工作日判定的關係**~~ → **已由決策 H 取代**：工作日判定改以
  `stopReason`（`WorkStopReason` 列舉）為唯一權威來源，天氣完全退出判定，
  舊的「天氣含雨且敘述含停工」啟發式已移除。E3 日後落地時，
  `NO_WORK` 只作交叉驗證，不參與 `classifyWorkDay`。
- **AI 判讀污染權威資料（E7-b）**：決策 A 使日報加總成為月報累計的權威來源，數量表判讀錯誤會直接影響月報金額與進度。必須維持「判讀只做預填、人工確認後才入帳」，不得自動送出；`unit` 一律取自 `WorkItem.unit` 而非文件。
- **判讀品項與工項的對應（E7-b）**：文件上的品項名稱未必等於台帳 `WorkItem` 名稱。比對不確定者應標記待確認而非猜一個 `workItemId`——錯誤關聯比留空更難察覺。契約外臨時項目維持 `workItemId: null`。
- **法定格式版本差異**：各主辦機關的日報格式未必一致（範例來自單一機關）。若需支援多機關，應考慮「章節定義可配置」而非寫死五章——此為較大架構決策，建議先確認實際需求範圍。

## 刻意延後的項目（2026-08-08）

以下在缺陷檢視中確認存在，但都不是資料正確性問題，且各需跨模組變更，
故與缺陷修正分開。記在這裡以免被當成「已經沒事了」。

| 項目 | 現況與理由 |
| --- | --- |
| `SupervisionReport` 硬刪除 | schema 內約 20 個 model 有 `deletedAt`，本表沒有，刪除為實刪且 `SupervisionReportItem` 連帶 cascade。稽核 snapshot 現已保存完整內容故可還原，但需人工讀 JSON。改為軟刪除要在每個查詢加過濾條件，宜單獨一次做完 |
| `SupervisionReportItem` 缺 `@@unique([reportId, workItemId])` | 程式已能正確處理重複列（成組比對＋相加，且合併會留下軌跡），新資料因 `parseQtyEntries` 合併而不會產生。但資料庫層無防線；既有資料若已有重複，加約束會讓 `db push` 直接失敗，需配清理腳本 |
| repository 仍持有部分政策 | `upsertDraft` 內含「同期只留一份 DRAFT」的政策與硬寫的狀態字面值。查詢述詞用字面值可接受，政策放取數層不行 —— 另行處理 |
| 取消產製無法回收 LLM 花費 | 伺服器已在寫入前檢查連線是否中斷（不會留下沒人讀過的草稿），但 LLM 呼叫本身需把 `request.signal` 一路接進 `faith.service` 才能中止 |
