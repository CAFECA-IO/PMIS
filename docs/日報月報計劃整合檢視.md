# 日報 × 月報 計劃整合檢視（定案）

> 目的：確立「**日報為單一真實來源（SSOT）、月報為衍生層**」的統一資料架構，並記錄三項定案決策對「已完工月報」的回改範圍。
> 日期：2026-08-05
> 關聯：
> - `監造日報填報擴充規劃.md`（上游，規劃中）
> - `AI彙整報告改用監造月報範本_執行計劃.md`（下游，M1–M8 已完工上線）
> - `AI彙整報告生成流程重新設計.md`（白名單數據集流程）

## 定案決策（2026-08-05）

| 代號 | 決策 | 直接影響 |
| --- | --- | --- |
| **A** | 月報所有數據一律取自日報 | 日報 = 單一真實來源；月報不再自有獨立資料源 |
| **B** | 月報須與日報同步升級 | 已上線月報碼隨日報改動一併調整，不得各做各的 |
| **C** | 使用者只在日報填「每日（實際）進度」；當日「預定進度」由系統依專案「預定進度設定」自動推算 → **需新增設定專案「預定進度」的地方** | 新增專案級 schema + 設定入口；日報 E5 的預定欄由人工鍵入改為系統自動帶入 |
| **D** | **天氣欄位僅供紀錄**；停工／工期判定一律以 `summary` 為主（輔以 E3／E5 顯式旗標），不以天氣為依據 | E4「天氣拆上午／下午」失去主要理由 → 降為選配純紀錄；`classifyWorkDay()` 移除天氣訊號 |
| **E** | **表報編號由系統自動產生流水號** | 確認 E6 `serialNo`：依專案內 `reportDate` 決定論排序產生，無人工編號、避免衝突 |

> **C 的理解確認**：每日僅輸入實際（數量／進度），當日「預定進度」不由人工鍵入，而由系統查專案的「預定進度基準線」自動算出並比對落差；因此需補一個「設定專案預定進度」的地方。

## 統一資料架構（Before / After）

**舊（月報 M1–M8 上線時的假設）**

| 數值 | 來源 |
| --- | --- |
| 累計完成 | `WorkItem.completedQty`（台帳人工值） |
| 本期預定／完成 | 履約事項權重（`periodProgressDelta` / `getSCurve`） |
| 工作日分類（施工／雨停／例假） | `classifyWorkDay()` 文字啟發式（猜 `weather`／`summary`） |
| 逐工項本期完成 | `WorkItemPeriodSnapshot`（待辦，未做，顯示 `—`） |

**新（三項決策定案後）**

| 數值 | 來源 | 依據 |
| --- | --- | --- |
| 實際進度（累計／逐工項） | 日報加總（`SupervisionReportItem.dailyQty` 期間之和） | 決策 A |
| 預定進度 | 專案「預定進度設定」基準線（**新增**） | 決策 C |
| 工作日／停工認定 | `summary` 敘述為主 ＋ E5 `excludedFromDuration`（免計工期，法律效果）＋ E3 `NO_WORK`；**天氣不作判定、僅供紀錄** | 決策 A、D |
| 逐工項本期完成 | 日報 `dailyQty` 期間加總（**取代快照**） | 決策 A |
| 表報編號 | 系統依 `reportDate` 決定論產生流水號（E6 `serialNo`） | 決策 E |

## 對已完工月報的回改清單（決策 B）

| 月報既有產出 | 現狀 | 回改動作 |
| --- | --- | --- |
| `WorkItemPeriodSnapshot` 月結快照待辦 | 規劃中、未做 | **取消**，改由日報 E1 加總 |
| 累計完成讀 `WorkItem.completedQty` | 已上線 | 改接日報加總；台帳值降為推導／對照顯示 |
| `getSCurve` / `periodProgressDelta`（履約事項權重） | 已上線 | **實際線**改接日報加總；**預定線**改接專案預定進度設定 |
| `classifyWorkDay()`（原用 `weather`＋`summary` 猜測） | 已上線 | 停工／免計工期改以 E5／E3 顯式旗標為準、`summary` 為輔；**移除 `weather` 作為判定依據**（決策 D） |
| `report-template.ts` 逐日日誌讀 `summary`／`weather` | 已上線 | 隨 E2／E4 欄位拆分同步改讀新欄位（漸進遷移、legacy fallback） |

> **關鍵警示**：決策 A 讓 `WorkItem.completedQty` 從「權威」降為「推導」。其他既有畫面（dashboard 等）若也讀此欄，須一併確認改讀衍生值後不受影響，避免出現兩套數字。

## 新增工作：專案「預定進度設定」（決策 C 帶出）

兩份原計劃都沒有涵蓋的新缺口。日報 E5 原本設計 `plannedProgress`（當日預定）與 `actualProgress`（當日實際）兩個人工欄位；依決策 C，**`plannedProgress` 改為系統自動帶入，不再人工鍵入**，其來源即此設定。

- **schema**：專案級預定進度基準（候選形態見〈待確認〉）。
- **用途**：
  1. 自動帶入日報 E5「當日預定進度」（免監造每日鍵入）
  2. 繪製 S-Curve 的**預定線**
  3. 計算落差（實際 − 預定）
- **入口**：專案設定頁新增「預定進度」設定區。

## 合流後的階段順序（修訂）

把兩份計劃的階段合併，並標出交會點：

| 階段 | 內容 | 交會點 |
| --- | --- | --- |
| **第 1 階** | 日報 **E1 數量表** ＋ **專案預定進度設定** | 同時打通月報 3.3（逐工項本期完成）與 S-Curve 兩條線；月報累計來源切到日報加總。〔決策 A＋C 的核心〕 |
| **第 2 階** | 日報 **E3 職安衛三態／E5 免計工期**（E4 天氣拆分降為選配） | 月報 `classifyWorkDay()` 改以 E5／E3＋`summary` 判定；工作日統計、免計工期改為可統計 |
| **第 3 階** | 日報 **E2** 五章拆分 | 月報逐日日誌組裝同步改讀新欄位 |
| **第 4 階** | 日報 **E6** 表報編號（系統流水號）／簽章 | 流水號決定論產生可先行；簽章依賴簽核流程 |
| **第 1 階（併入）** | 日報 **E8** 施工照片（綁 `reportId`／`reportItemId`） | 相依 E1 的 `SupervisionReportItem`；月報後續若要附照片可由此取數 |
| **第 5 階** | 日報 **E7-a** 單筆欄位判讀（接既有 `form-assist`） | 低成本接線，與月報無直接相依 |
| **第 6 階** | 日報 **E7-b** 數量表多列判讀（仿 `wizardExtract`） | ⚠️ 因決策 A，判讀結果會成為月報累計的權威來源 → 須「人工確認後才入帳」 |

> 每一階的「日報側改動」與「月報側回改」須綁在**同一個工作項**內驗收（決策 B），不可只改一端。

## 待確認

- **預定進度設定的資料形態**：里程碑式 / 月度累計 % / 或沿用並顯性化既有「履約事項權重＋到期日」。三者都能推算「當日預定」，但輸入負擔與精細度不同。建議先確認貴單位手上「預定進度」原本以什麼形式存在（通常是預定進度表或 S 曲線），據以定案。
- **履約事項的定位**：原本履約事項權重同時供「預定」與「實際」；拆成日報（實際）＋預定進度設定（預定）後，履約事項是否僅剩里程碑管理、或即作為預定進度來源，需釐清以免三者重複。
- **台帳一致性**：`WorkItem.completedQty` 降為推導後，寫入端（人工更新入口）應同步關閉或改為唯讀，避免與日報加總並存產生第二來源。
- **E7-b 判讀與決策 A 的交互作用**：日報既為月報累計的單一真實來源，數量表的 AI 判讀錯誤將直接污染月報金額與進度。E7-b 須維持「判讀只做預填、人工確認後才入帳」，且判讀品項與 `WorkItem` 的對應不確定者應標記待確認而非猜測 `workItemId`。詳見日報計劃 E7。
- **停工「可統計性」依賴顯式旗標（決策 D 的配套）**：天氣既不作判定，停工／雨停／免計工期的統計就不能靠解析 `summary` 純文字（會重演舊啟發式的不可靠）。因此 E5 `excludedFromDuration`／E3 `NO_WORK` 這兩個顯式旗標必須在表單上「一鍵好勾」，並由它們（而非 summary 文字）驅動統計；`summary` 僅供人閱讀與佐證。建議沿用日報計劃的「停工日一鍵套用」設計確保旗標被確實記錄。
