## 決策 F 的完整理由（`WorkItem.progress` 為何保留欄位）

> 自 工項累計量與進度來源改造.md（原名 completedQty_盤點.md）併入；該檔已於 2026-08-06 退場。
> 這段是最容易被後人「順手清掉」的判斷，故留在此處。

**`progress` 不能改為純推導**，原因不是效能，而是**有一群工項根本沒有可推導的來源**：

1. **新建的工項天生「無數量」。** `constant/form-assist.ts` 的 `work-item` 規格欄位為
   `name`／`category`／**`progress`**／四個日期——**沒有 `contractQty`，也沒有 `unit`**。
   經表單或費思助手新增的工項，一開始只有人工填的進度、沒有數量。
   「無數量工項」不是邊緣情形，而是新建工項的預設狀態。
2. **現行程式已刻意支援此情形。** `progressFromQty()` 在數量不齊時回 `null`，
   代表沿用人工填的百分比（見 `work-item-ledger.ts` 該函式註解）。
3. 若改為純推導，這些工項的進度會變成 `null` 或 0，而 S 曲線（`scurve.ts`）
   與履約事項上捲（`obligation-rollup.ts` 經 `derivedProgress` → `effectiveObligationActual`）
   直接讀 `progress` ——結果是**新建工項的進度從曲線上消失**。這是不可接受的迴歸。

**因此的設計**：`progress` 欄位保留，語意收斂為「人工填報進度」——
未計量工項的唯一來源、已計量工項的後備值。下游一律讀**有效進度**：

```
effectiveProgress = progressFromQty(期初 + Σ日報dailyQty, contractQty) ?? progress
```

**為何推導值不回寫欄位**：累計量會隨日報填報隨時改變，回寫等於同時存在兩份資料，
只要有一個寫入路徑忘了重算，就會出現「日報已更新、S 曲線仍是舊值」而兩邊都自稱正確。
不存推導值則此類 bug 無從發生。這也與 `WorkItem` schema 既有明訓一致：
契約複價與完成率一律推導、不另存欄位。

**實作位置**（2026-08-06 完成）：`obligation-rollup` 與 `scurve` 的純函式**未改動**；
改為在 4 個取數點以 `withEffectiveProgressAll` 換算後餵入——
`project.service` 的 `getWorkItemDetails`／`getProject`／`listProjects`，
以及 `dashboard.service.getSCurve`。`ledger.service` 的 `progress` 回寫已移除。

> 註：`obligation-completion.checkCompletion` 刻意**不看** `progress`
> （只看 `status`，避免兩套標準），故不在換算範圍內。

## 「累計」一律要有時間上限（2026-08-07 修正）

決策 A 把累計改為由日報加總推導後，第一版的月報取的是**全期間**加總：

```ts
// 錯：沒有上限
const totals = await loadDailyQtyTotals(projectId);
const wiDetails = await getWorkItemDetails(projectId);
const cumulativeActual = derivedProgress(wiDetails);
```

於 8/7 補產 2 月月報時，3–7 月的數量會被算進 2 月的「累計完成」，
而「累計預定」用的是期末（2/28）—— 兩邊不同界，結果印出
「累計超前 53.88 個百分點」這種當時並不存在的數字。月報是送審文件。

更糟的是同一個 codebase 裡的日報進度條（`getDailyProgress`）本來就以當日為界，
於是同一天會出現兩個「累計完成」——正是決策 A 要消滅的問題，只是搬到了時間軸上。

**規則**：任何「累計」都必須指定時間上限，且與同一份報表的其他累計欄位同界。

- 取數：`loadDailyQtyTotalsUpTo(projectId, asOf)`（`daily-qty.service`），
  下界取紀元而非開工日 —— 開工日可能未填或晚於既有日報，以它為界會靜默丟棄紀錄。
- 有效進度：`getWorkItemDetails(projectId, asOf)`。**產製期間報表時必須給定期末**；
  省略僅適用於畫面即時顯示（台帳、儀表板）。
- 例外並記：日報填報表單的「目前累計」刻意取全期間 ——
  那是判斷「超出契約數量」的輔助，不是報表數字。

## 預定與完成必須算在同一批工項上（2026-08-07 修正）

與上一節同一類錯誤，只是搬到母體上。`plannedProgressAt` 只取具預定起訖日的
工項（未設定者沒有預定值可比），而 `weightedProgressDelta` 與
`derivedProgress` 走全部工項（未排程者權重 1）。兩側母體不同，落差就憑空生出：

> 1 個排程工項做完 100%，另有 20 個無預定日的工項
> → 預定 100%、完成 60%，報表宣稱**落後 40 個百分點**。

該做的都做完了，數字卻說落後 —— 而這個數字會進入工期展延爭議。

**規則**：整體進度的預定與完成，母體一律為 `isSchedulable`（有預定起訖日）的工項。

- 母體定義收在 `scurve.isSchedulable`，`plannedProgressAt`／`weightedProgressDelta`／
  `buildWorkItemSCurve` 都用它；`weightedProgressDelta` **在函式內過濾**而非交由
  呼叫端自律 —— 先前正是靠呼叫端各自過濾而失守的。
- `report.service` 以單一 `basis` 變數餵給四個數字（累計預定、累計完成、
  本期預定、本期完成），不再各自取用不同陣列。
- 被排除的工項**不是被忽略**：其累計完成仍列於 3.3，且排除項數會在
  3.1 下方與註記表明白標示（`unscheduledWorkItems`）。
  20 項中只有 1 項參與比對時，「累計完成 100%」是誤導性的真話。
- 無可比對工項時，累計預定與累計完成皆為 `null`，呈現為「—」。
  **不得以 0 代入** —— 0 是「確實毫無進度」，缺值是「無從計算」，
  且落差算成 0 會寫出「與預定相符」，那是缺值時最容易被當真的一句話。

## 決策 J：為何只記錄、不上鎖

> 自 待定決策清單_H-M.md 併入；該檔已於 2026-08-07 退場，決策 H–M 已納入上方決策表。

原本規劃「日報核定後鎖定不可修改」。討論中確認兩件事後改變了做法：

**1. 日報現階段是監造的施工紀錄本，簽核流程尚未實作。**
`SupervisionReport.status` 的 `APPROVED` 只是表單上的一個下拉選項——
唯一的守門是 `currentUserCanEdit("/logs")`，**寫報告的人可以自己把它設成已核備**。
據此上鎖只會提供**假的保證**，讓人以為文件受保護，比沒有鎖更危險。
待正式簽核流程上線（接既有的 `ApprovalDocument`／`ApprovalWorkflow`）再議。

而且對紀錄本而言這是合理的：紙本施工紀錄本本來就允許更正，
規矩不是「不准改」而是**改了要看得出來**（劃線、蓋章）。變更軌跡就是數位版的那個規矩。

**2. 真正的破口不在日報，而在月報沒有留存。**
`GeneratedReport` 原本只是一個 TypeScript 回傳型別，月報完全不存檔。
月報的每個數字都是即時推導（決策 A／F／I），同一期間在不同時間產生會得到不同結果
——「送審出去的是哪一版」在系統中根本不存在。
治理原則要求的「生成結果為草稿，須經人工確認後方可歸檔」亦無處標記。

故拆為兩件實作：

| | 內容 |
| --- | --- |
| **J-a 月報留存** | `GeneratedReport` 持久化，存 markdown 全文與 `DRAFT`／`CONFIRMED` 狀態。已確認者不可修改刪除、同期僅允許一份定稿。**月報定稿即為當時數字的快照**，日報事後修正不影響已定稿報表 |
| **J-b 日報變更軌跡** | `SupervisionReportAuditLog`，記錄欄位異動、狀態轉換、數量表變更與整份刪除。刻意不設外鍵，使日報刪除後軌跡仍存在 |

### J-b 的兩條底線（2026-08-07 補）

**一、摘要會截斷，所以每一種動作都必須另存未截斷的完整快照。**
軌跡列表若塞滿整段敘述就沒人會讀，故摘要中的值一律截斷 —— 但截斷過的摘要
是提示、不是紀錄。`summary` 若是 81 字、結尾為「…經監造確認符合契約第 7 條
免計工期之情形。」，只留 60 字摘要而 DB 欄位又被新值覆寫，那句直接對應金額的話
就從 DB 與軌跡兩邊同時消失。故 `describeFieldChanges`／`describeCreation`／
`describeQtyChanges`／`describeDeletion` 一律回傳 `AuditDetail { summary, before }`，
`before` 是未截斷的 JSON，服務層以「摘要\nJSON」寫入 `detail`。

**二、摘要與快照放兩個欄位，不靠嗅探換行。**
`detail`（摘要，可能含使用者原文與換行）與 `snapshot`（未截斷的完整 JSON）
是 `SupervisionReportAuditLog` 上的兩個欄位。先前以「第一個換行之後即為 JSON」
切分，遇到 `施工概況：上午澆置\n下午養護` 就會把後半段標成「變更前明細」——
出現在一列 CREATE 上，而 CREATE 根本沒有變更前。

**三、契約外項目沒有身分，只能成組比對。**
先前以 `x:${itemName}` 當 Map 鍵，同名兩列會靜默收斂成最後一筆：
報表有「雜項 3」與「雜項 7」時刪掉第一列，before 與 after 的鍵都指向 7，
比對結果為「無異動」而**完全不寫軌跡** —— 3 已從累計與估驗金額中消失卻零紀錄。
現行：台帳工項以 `workItemId` 逐項比對（並在 `parseQtyEntries` 合併重複工項，
使該索引唯一）；契約外同名列整組比對，變更呈現為「雜項 3m、7m → 7m」。
任何配對方式都是猜測（那兩列本來就分不出誰是誰），成組呈現不需要猜，也不漏任何一列。

> J-a 同時解決了先前反覆出現的快照問題：日報的當日預定／實際進度**不需要**存欄位，
> 因為要保存的是「送審那份文件的數字」，而那正是月報定稿。

### J-a 的實作要點：產出即留存，不設「留存」按鈕（2026-08-07 修正）

初版把留存做成一顆獨立按鈕，按下時**重跑一次產製**。這是錯的：
報表數字是即時推導、期間評述由 LLM 現寫，10:00 預覽、10:10 按留存，
存下來的必然不是使用者讀過的那一份 —— 接著按「確認定稿」，
就凍結了一份沒人讀過的送審文件，而按鈕上還寫著「保存目前這一版」。

現行做法：

- **產製是明示動作**（2026-08-07 再修正）。初版把「產出即留存」接在自動產製上，
  於是光是打開 `/logs` 就跑一次付費 LLM 產製並寫一列草稿；
  更糟的是 `<input type="date">` 在年份欄逐鍵觸發 change，
  輸入 2026 會依序送出 0002／0020／0202／2026 —— 四次產製、四列永久草稿
  （西元 2 年、20 年、202 年各一列）。
  現行：掛載與切換期間走**唯讀**的 `getPeriodReport`（不呼叫 LLM、不寫入），
  只有按下「產生報表」才走 `generateReportView`。
  基準日的合理範圍（2000–2100）守在伺服器端的 `parseRefDate`，
  用戶端防抖只是減少請求，擋不住直接打 API。
- 產製與留存在同一次呼叫內完成（`report.service.generateReportView`），
  回傳的 markdown 與寫進 `GeneratedReport.markdown` 的是同一個字串。
- 同一專案／週期／期間只保留一份草稿，重新生成即覆寫
  （`generatedReport.repository.upsertDraft`，亦為該表唯一寫入入口）。
  切換週期或日期因此不會堆出大量草稿。
- 本期已有定稿時**不覆寫、也不另存草稿**：定稿是凍結內容，
  而預覽仍須顯示現況，否則使用者無從發現現況已與定稿不同。
  此時畫面明確標示「不作為送審依據」。
- **定稿帶版本守門**（2026-08-07 再修正）。草稿是同一列原地覆寫，
  所以 id 不足以指明「哪一版」：A 分頁 09:00 讀到的內容，可能在 09:05 被
  另一個分頁或同事的重新生成覆寫成別的東西，而 A 分頁的畫面與 id 都沒變 ——
  按下確認就凍結了一份沒人讀過的送審文件。這與「按鈕另跑一次產製」是同一個
  失效模式，只是觸發點不同。
  故 `confirmSavedReport` 必填 `expectedGeneratedAt`（畫面上那一份的產出時間），
  伺服器比對不符即拒絕並提示重新檢視。用戶端擋不住另一個分頁，守門必須在伺服器端。
- 留存清單每一列可展開讀全文（`openSavedReportAction`）——
  只列 metadata 而讀不到內容，等於存進去再也打不開。
  展開的內容連同讀取當下的版本一起記住；清單每次重載都重新驗證，
  版本不符即收起並提示重新開啟 —— **不靜默替換眼前的內容**，
  否則使用者會讀著舊版按下定稿。
- **期間身分用文字鍵 `periodKey`**（如 `MONTHLY:2026-08`），不用 `periodStart` 相等比對。
  後者由伺服器時區推導，部署時區一改（UTC → Asia/Taipei）既有列就對不上：
  `upsertDraft` 開始堆重複草稿、`findConfirmedForPeriod` 靜默回 null，
  「同期只有一份定稿」的守門會**無聲**關閉。
- **基準日只解析一次**：`parseRefDate` 在 `generateReportView` 解析後把 `Date`
  往下傳。先前 `generateReport` 會再讀一次時鐘，跨月的午夜前後產製時
  `periodLabel` 與 `periodKey` 會落在不同月份。
- `/api/report` **不接受 `DAILY`**：日報是 `SupervisionReport`，與彙整報表是兩種東西。
- 清單的**定稿不與草稿共用截斷**：定稿全數列出，草稿取最近 30 份。
  清單是唯一能開啟定稿的 UI，草稿把定稿擠出去等於讓已送審文件消失。
- 無編輯權限者只讀不寫：純瀏覽不應在留存清單留下紀錄。

## 新建日報不得覆蓋既有日報（2026-08-07 修正）

`fileReport` 原本是 upsert（同日期以更新處理），但新建表單**不會載入既有內容**：
文字欄位一律從空白開始，送出時每個空輸入都寫成 `null`。

失效樣態：8/3 已有一份 APPROVED 日報（完整施工概況、勾了免計工期並填依據、3 列數量）。
使用者從頁首開「新建日報」、把日期改成 8/3、什麼都不打就送出 →
所有文字欄位變 `null`、`excludedFromDuration` 變 `false`、依據消失、
APPROVED 降回 DRAFT。數量列還在卻不再計入累計，該月估驗金額隨之變動。
使用者看不到自己刪掉了什麼。

**附帶**：數量表的 `note` 必須在表單上顯示並帶回。它先前寫得進 DB 卻讀不到，
於是監造開啟日報存個檔就會把它寫成 `null` —— 刪掉一句自己從沒看過的話，
而備註常是免計工期或數量異常的唯一書面理由。

**規則**：「新建」只做新建。同日期已有日報時 `fileReport` 直接拒絕，
並指引使用者改由日誌開啟該日日報編輯（`updateReport` 會先載入現有內容，
使用者改的是看得見的東西）。新建表單另於選定日期當下即時提示
（`checkReportDate`）—— 伺服器會擋，但等使用者打完一整份才退回太晚了。

## 決策 K：SUBMITTED 是否足以計入累計

治理原則寫「核定、簽章、退件等決策一律保留給監造人員」，
故曾考慮把計入條件收緊為僅 `APPROVED`。**結論是維持 SUBMITTED＋APPROVED。**

兩個理由：

1. **`APPROVED` 目前不代表任何程序**（見〈決策 J〉），收緊並不會換得任何實質保證。
2. 日報是施工紀錄本，兩個狀態的實際語意是 **DRAFT ＝ 還在填、SUBMITTED ＝ 填完了**。
   「這天我填完了」正是數字該不該算數的分界，與簽核無關。

> 原先以「未經簽核的數字不該驅動報表」立論。確認日報無簽核流程後該理由不成立，
> 已於 2026-08-07 更正為上述說法。結論不變，但理由不同 —— 記錄在此以免後人沿用錯誤前提。

## 決策 C 的修正（2026-08-07）：不需要新增「預定進度設定」

> 先前判斷「兩份原計劃都沒有涵蓋此缺口，需新增專案級 schema 與設定入口」——
> **該判斷有誤**，因為當時未查 PMIS-04 時程進度管理模組。系統早已具備預定進度基準。

**既有的兩套預定進度基準**（`src/service/scurve.ts`，使用者可於專案頁以 `CurveBasisToggle` 切換）：

| 基準 | 預定累計 % 的算法 | 曲線形狀 |
| --- | --- | --- |
| 履約事項（`OBLIGATION`） | 期限 ≤ 該時點的履約事項權重 ÷ 總權重 | 階梯式（過期限才跳一級） |
| **工程分項（`WORKITEM`）** | Σ(權重 × `plannedFrac`) ÷ 總權重；權重＝預定工期天數，`plannedFrac = clamp01((時點 − plannedStart) ÷ (plannedEnd − plannedStart))` | **線性平滑** |

**定案：日報的「當日預定進度」採工程分項基準。**
階梯式的值放進逐日欄位會出現「連續數十天不動、然後跳數個百分點」，
監造無從判讀當日落差；工程分項基準每天都有合理增量，本質上就是一張預定進度表。

**因此 E5 的實作是**：抽出一個 `plannedProgressAt(items, date)` 純函式
（`buildWorkItemSCurve` 內的 `plannedFrac` 已具備此能力，目前只在每個月底取樣），
日報填報時以報表日期呼叫即可自動帶入。

- **零 schema 改動**：不新增任何欄位或資料表。
- **零新增設定介面**：基準線的來源是工項的 `plannedStart`／`plannedEnd`，
  其建立與更新入口已存在（`src/app/projects/actions.ts` 的工項 create／update）。

> **待確認的一致性問題**：月報 S 曲線的基準是**使用者可切換的**，而日報固定用工程分項基準。
> 若使用者把月報切到履約事項基準，日報與月報的「預定進度」會不一致。
> 兩個選項：(a) 日報固定工項基準並在畫面註明基準，(b) 日報跟隨專案的曲線基準設定。
> 目前採 (a)，因為日報是法定文件、其數值不宜隨檢視偏好改變。

- **schema**：專案級預定進度基準（候選形態見〈待確認〉）。
- **用途**：
  1. 自動帶入日報 E5「當日預定進度」（免監造每日鍵入）
  2. 繪製 S-Curve 的**預定線**
  3. 計算落差（實際 − 預定）
- **入口**：專案設定頁新增「預定進度」設定區。

## 2026-08-08 缺陷修正批次：三個反覆出現的樣態

這一輪修的問題彼此看似無關，但歸納起來只有三種樣態。記下來是因為
**它們會再犯**，而每一次的表現都是「畫面正常、數字正常，只是錯了」。

### 一、身分鍵由不穩定的東西推導

`periodStart` 是絕對時點卻被當成期間身分；改成文字鍵之後，
產生鍵的函式又以本地取值讀 UTC 解析出來的 Date。
兩次都是同一個錯誤：**身分必須由使用者心中的那個東西（日曆日）決定，
不是由它在某個時區下的瞬間表示決定。**

對策：`period-key.ts` 收斂為單一來源，跨時區行為測試釘住。
回填腳本改為匯入同一份，不再手抄。

### 二、TOCTOU：查到的東西在寫入前變了

`upsertDraft` 先 `findFirst({status:"DRAFT"})` 再 `update({where:{id}})`，
中間隔著一次 LLM 產製（以秒計）。若那段期間有人把它定稿，
就會改寫**已凍結的送審依據**，而該列仍顯示 CONFIRMED、仍帶對方的定稿時間。

對策：把狀態納入寫入條件（`updateMany({where:{id, status:"DRAFT"}})`），
更新到 0 列即代表「它已經被定稿了」，改為另建草稿。
同一類還有「確認定稿」——改為必填 `expectedGeneratedAt` 版本守門。

> 一般化：**凡是「先查再寫」而中間有 I/O 的地方，查詢條件必須整條帶進寫入。**

### 三、以 Map 建索引，重複鍵靜默收斂

`new Map(rows.map(r => [key, r]))` 遇到重複鍵只留最後一筆。
數量表出現過兩次：契約外同名項目、以及同一 `workItemId` 的多列（歷史資料）。
後果是**刪掉一列卻比對出「無異動」而完全不寫軌跡**，量從累計消失且零紀錄。

對策：一律成組（`groupBy`）而非建索引；`loadQtyForm` 對重複列相加而非取後者。
`SupervisionReportItem` 仍缺 `@@unique([reportId, workItemId])`（見〈刻意延後〉）。

### 順帶修正的呈現層問題

這些不影響資料，但會讓人讀錯報表或誤以為系統壞掉：

- 專案軌跡靜默截在 200 筆，而標題宣稱「含已刪除」→ 改為分頁並揭露還有更早的紀錄。
- 留存清單與產製面板的錯誤訊息**永遠不會顯示**（都被「尚無資料」蓋掉，
  或根本沒有 `.catch` 而卡在載入中）→ 兩處都改為錯誤優先呈現。
- 3.2 進度圖同一圍欄內混有 2 欄與 3 欄的資料列 → 改為整欄一致，
  省略本期欄時另加註原因（否則讀圖者分不出「本期為 0」與「沒有本期資料」）。
- `/api/report` 只檢查專案成員，未檢查 `/logs` 模組權限 → 非編輯者可反覆觸發
  LLM 產製而不留任何痕跡。已補模組權限檢查。

## 遷移紀錄：`periodKey`（2026-08-08）

期間身分由 `periodStart` 相等比對改為文字鍵 `periodKey` 時，
既有的 `GeneratedReport` 需要回填。本專案採純 `db push`、無 `migrations` 目錄，
故 **`prisma/backfill-period-key.ts` 即是該次變更的唯一遷移紀錄**，

執行：`npm run db:backfill`（預覽）→ `npm run db:backfill -- --apply`。
三步驟（暫加 `@default("")` → 回填 → 移除）寫在該檔開頭，
README〈既有資料庫的結構升級〉亦有同一份說明。

主開發資料庫已完成（4 筆草稿）。

### 為何鍵的**推導**也必須與時區無關

改用文字鍵解決的是「已存的值不隨部署時區改變」，但**產生那個鍵的函式**
原本仍以本地取值讀一個 UTC 解析出來的 Date：
`new Date("2026-01-01")` 是 UTC 午夜，在 UTC−5 讀出來是 2025-12-31，
於是使用者選 2026 年年報、系統覆寫的是 2025 年的草稿。
UTC+8（本專案部署時區）與 UTC 不受影響，故這是潛在風險而非當時的線上缺陷。

**現行做法**：純日期字串一律以**本地日曆日**解析（`period-key.parseRefDate`），
鍵由同一支 `periodKeyFor` 產生，並以跨時區（UTC+8／UTC／UTC−5）行為測試釘住。

### 回填腳本的時區前提

`periodStart` 在資料庫裡是絕對時點，腳本以本地取值把它讀回日曆日 ——
這只在「腳本執行的時區＝當初寫入的時區」時才正確。
台北寫入的八月報表存為 `2026-07-31T16:00:00Z`，在 `TZ=UTC` 下會推出
`MONTHLY:2026-07`，而應用程式查八月用的是 `MONTHLY:2026-08`：
**該列定稿從此永遠查不到，且定稿不可刪改、產品內無從修正。**

故腳本會拿推導鍵反推的標籤與既有 `periodLabel` 比對，
不一致即中止並提示以正確時區重跑（`TZ=Asia/Taipei npm run db:backfill -- --apply`）。
算法也改為直接匯入 `period-key`，不再是手抄的第二份實作。

### 過渡期的空鍵

步驟 1 與 3 之間，既有列的 `periodKey` 是空字串。
`@@unique([projectId, confirmedPeriodKey])` 遇到空字串會退化成
「每個專案只能有一份定稿」——定稿九月時會收到「八月已有定稿」這種
完全指不到原因的訊息。故 `confirmSavedReport` 在期間鍵為空時直接擋下，
並明說要先執行回填。

## 已知缺口（2026-08-08 決定延後，非阻塞）

以下兩項在缺陷檢視中確認存在，但都不是資料正確性問題，且各自需要跨模組的
變更，故與缺陷修正分開處理。記在這裡以免被當成「已經沒事了」。

### 一、`GeneratedReport` 沒有變更軌跡

**現況**：草稿是同一列原地覆寫（`upsertDraft`），所以「這份草稿在定稿前
被誰、在什麼時候、改成過什麼」只留得下最後一版。日報有
`SupervisionReportAuditLog`，彙整報表沒有對應機制。

**為何可以延後**：定稿後內容凍結且不可刪除，送審依據本身是安全的；
且定稿帶版本守門（`expectedGeneratedAt`），不會凍結到沒人讀過的內容。
缺的是「定稿前的歷程」，屬於稽核完整性而非數字正確性。

**要做的話**：比照 `SupervisionReportAuditLog` 的形狀新增
`GeneratedReportAuditLog`（或共用同一張表加上 `targetType`），
在 `upsertDraft`／`confirm`／`remove` 三處於同一交易內寫入。
決策 J-b 已確立「摘要 + 未截斷快照分欄」的作法，直接沿用即可。

**相關**：刪除草稿目前沒有版本守門（過期的分頁可能刪掉剛被重新產生的那一份）。
草稿可再生，傷害有限，但若補軌跡宜一併補守門。

### 二、日曆日的 UTC／local 慣例尚未統一

**現況**：`SupervisionReport.reportDate` 是**日曆日**，由
`new Date("YYYY-MM-DD")` 產生，JS 對純日期字串一律以 **UTC 午夜**解析；
而 `periodRange` 的期間邊界、`formatDate`、`report-period.monthLabel`、
`buildWorkItemSCurve` 的分桶都用**本地**取值。

**已處理的部分**：
1. 凡是要與 `reportDate` 比較的查詢邊界，已一律換算成同基準
   （`report.service` 的 `utcDayStart`／`utcDayEnd`，以及 `getDailyProgress` 的日界）。
   所以**數字是對的** —— 在 UTC 偏移為負的部署中
   「當月第一天的數量整個消失」那個缺陷已經不存在。

   > **補記（2026-08-08，回饋指出）**：這句話當時**並不完全成立**。
   > `generateReport` 的同一批取數裡，三個查詢用換算後的 `qEnd`，
   > 只有 `getWorkItemDetails(projectId, end)` 傳本地邊界 ——
   > 而它內部走 `loadDailyQtyTotalsUpTo`，是同一條會比對 `reportDate` 的路徑。
   > 在 UTC−5 產二月月報時，3/1 的日報會被算進 §3.1 的累計進度、
   > 卻不算進 §3.3 的累計數量與金額。已修正為 `qEnd`。
   >
   > 更值得記的是**為什麼沒被抓到**：兩條守門測試各自只檢查自己那幾個呼叫，
   > 其中一條還把 `getWorkItemDetails(projectId, end)` 寫進正規式，
   > 等於把缺陷鎖成規則，並與另一條互相矛盾。
   > 現已改為對整個取數區塊斷言「不得以本地 `start`／`end` 當查詢界」——
   > **逐個列舉的守門會漏掉沒被列舉的那一個。**
2. **期間身分鍵**（2026-08-08）：`parseRefDate` 對純日期改以本地日曆日解析，
   `periodKeyFor` 因此在任何時區都對同一個日曆日產生同一個鍵，
   並有跨時區行為測試。詳見上方〈遷移紀錄：`periodKey`〉。

**還沒處理的部分**：**顯示與分桶**仍是本地取值 —— `formatDate`、
`report-period.monthLabel`、`buildWorkItemSCurve` 的分桶。
在負偏移部署（如 UTC−5）中，週報標籤與 S 曲線的月分桶可能偏一天，
月初的點會落到上一個月的桶。**數字正確、標籤可能錯月。**
UTC+8（本專案的部署時區）與 UTC 不受影響。

**要做的話**：把「日曆日」與「時間點」在型別或命名上分開，
`formatDate`／`monthLabel`／`buildWorkItemSCurve` 對日曆日改用 UTC 取值
（另立 `formatCalendarDate` 之類，不影響 `createdAt` 這種真實時間點的顯示）。
會動到 `scurve` 的既有測試，宜單獨一次做完並補上時區測試，
不要夾在其他修正裡。

### 三、其餘刻意延後的項目

| 項目 | 理由 |
| --- | --- |
| `SupervisionReport` 硬刪除（其他約 20 個 model 有 `deletedAt`） | 稽核 snapshot 現已保存完整內容，可還原但需人工讀 JSON。改軟刪除要在每個查詢加過濾，宜單獨一次做完 |
| `SupervisionReportItem` 缺 `@@unique([reportId, workItemId])` | 程式已能正確處理重複列，新資料不會產生；但既有資料若有重複，加約束會讓 `db push` 失敗，需配清理腳本 |
| `upsertDraft` 仍持有「同期只留一份 DRAFT」政策 | 查詢述詞用狀態字面值可接受，政策放取數層不行 —— 另行處理 |
| 取消產製無法回收 LLM 花費 | 伺服器已在寫入前檢查連線中斷（不留下沒人讀過的草稿），但要中止 LLM 需把 `request.signal` 接進 `faith.service` |
| `package-lock.json` 被刪除並列入 `.gitignore` | 與日報功能無關的倉庫級變更，`npm ci` 因此不可用；宜獨立處理 |

> 同一份清單亦列於 `監造日報填報擴充規劃.md`〈刻意延後的項目〉，兩處請一併維護。
